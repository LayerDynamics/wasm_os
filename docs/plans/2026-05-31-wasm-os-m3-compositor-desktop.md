## What desktop compositor is

A **windowed desktop inside the tab**: a host-side compositor that manages real windows (move/resize/focus/min/max/close + z-order), a taskbar with a launcher and clock, and — the new substrate — **process-owned graphical windows**. A WASI process requests a surface via a new `win_surface` kernel call, draws pixels into a shared framebuffer, and the compositor presents them to a `<canvas>`; the focused window's keyboard/mouse are **brokered to the owning process** through the capability system. The shell and userland terminal becomes one window (a DOM surface); the **file manager and three graphical apps are WASI processes** (canvas surfaces).

**Spec traces:** FR-21 (desktop: taskbar/launcher + clock + multiple windows), FR-22 (window lifecycle + z-order), FR-23 (surface = DOM **or** canvas/WebGL framebuffer), FR-24 (graphical file manager that browses the VFS and launches files), **FR-25** (input brokered to the focused window's process via capabilities — *included*), **FR-26** (theming/wallpaper persisted to `/home` — *included*), FR-31 (per-process capabilities incl. `Gpu`/`Input`), FR-36 (the new `win_surface`/input ABI is generated by the Binder from `wit/`). Carries forward FR-6 isolation and FR-34 crash containment under the compositor.

**Decisions confirmed for desktop compositor (from planning Q&A):**
1. The **file manager is a real Rust WASI process** (not a host DOM app) — it enumerates the VFS via `fd_readdir`, holds the `Spawn` cap, and renders a canvas surface with mouse navigation.
2. **Three sophisticated graphical apps** (proposed, adjustable at approval): **Paint** (Rust), **Text editor** (Rust/C), **Mandelbrot explorer** (Zig). Each is a process-owned canvas surface with input — not a passive framebuffer.
3. **FR-25 input brokering** and **FR-26 theming/wallpaper** are both in scope.
4. Tier A (SAB) only — the compositor + framebuffer + input paths use the existing SAB substrate; Tier B is out of scope for desktop compositor (consistent with the project's primary tier).

## Architecture deltas introduced by desktop compositor

- **Compositor (host, TypeScript, main thread)** — `packages/host/src/compositor/`. Owns a `Window` set: `{id, title, ownerPid?, surface: DOM|Canvas, geometry, state: normal|min|max, z}`. Window chrome (titlebar drag-move, resize handles, min/max/close), z-order, focus. Taskbar: launcher (spawn apps), running-window buttons, live clock. This is the new top-level UI; `packages/host/index.html` becomes a desktop root, and the terminal is mounted *inside a window* rather than full-screen.
- **`win_surface` kernel extension (new opcode `0x23`)** — a process calls `win_surface(kind, w, h)`; the kernel returns a `surface-request` in its `SyscallOutcome` (exactly like the shell and userland guest-spawn choreography). The kworker, on that request, asks the main thread to **create a window + allocate a per-surface framebuffer `SharedArrayBuffer`** (`w*h*4` RGBA), shares that SAB to **both** the owning process-worker and the compositor, and returns the `surface_id`. Pixels never travel through the ring.
- **`win_present` (opcode `0x24`)** — a tiny "frame ready" signal: the guest draws into its own linear-memory framebuffer, the process-worker's shim copies `[ptr..ptr+len]` into the shared framebuffer SAB, and posts a present signal; the compositor blits via `putImageData`/`createImageBitmap` on `requestAnimationFrame`. (Guest memory → framebuffer SAB is one copy in the worker that already has guest-memory access; isolation FR-6 preserved — the process never sees a peer's memory.)
- **Input brokering (FR-25)** — the compositor captures the **focused** canvas window's keyboard/mouse, and (capability-checked: owner holds `Input`) delivers events to the owning process via a new host→kernel `deliver_input(pid, event_bytes)` (sibling of shell and userland's `deliver_stdin`). The process reads them with `win_read_input(surface_id, buf)` (opcode `0x25`), which **parks/resumes** on `WaitReason::Input` — reusing the shell and userland park/resume machinery wholesale.
- **Capabilities** — `Gpu` (already in the enum) gates `win_surface`; `Input` (already in the enum) gates input delivery. Default-deny stays intact: a process without `Gpu` cannot get a surface; without `Input`, no events are delivered.
- **Guest graphics support** — `crates/wasmos-sys` has typed stubs for `win_surface`/`win_present`/`win_read_input`, checked by Binder against `wit/kernel/kernel.wit`; a small `crates/wasmgfx` helper crate (framebuffer ops: clear, put_pixel, fill_rect, blit, a 6×8 bitmap font, event decode) is shared by the Rust apps, with the equivalent for the Zig app.

**Message topology (unchanged hub):** guest ⇄ process-worker (ring) ⇄ kworker ⇄ main/compositor (postMessage). The kworker already orchestrates spawn, holds process-worker refs, and relays `term-output`; it now also relays surface creation + present signals and routes the framebuffer SABs.

## desktop compositor exit criteria (definition of done — from spec §4.1 / §5)

1. Boot reaches a **desktop**: taskbar with a working **launcher** and a live **clock**; the shell and userland terminal runs **in a window**.
2. **Window lifecycle works** for every window: open, close, **focus**, **move**, **resize**, minimize, maximize, and correct **z-order** (FR-22).
3. **Both surface kinds present concurrently** (FR-23): the terminal (DOM/xterm) and at least one **canvas** process-window on screen together.
4. The **file manager** (Rust WASI process) browses the real VFS and **launches a `.wasm` from the file manager** (double-click), and opens a `.txt` in the **text editor** by association (FR-24).
5. **Three sophisticated graphical apps** run as process-owned canvas windows, each **interactive** via brokered input (FR-25): Paint, Text editor, Mandelbrot explorer — at least one authored in **Zig** (FR-14 reinforcement on the graphics path).
6. **Terminal + file manager + ≥1 graphical app run concurrently** in separate windows; move/resize/focus all work across them; a crashing graphical app is **contained** (FR-34) — its window closes with an error, the desktop and peers survive.
7. **FR-26:** wallpaper + theme persist to `/home` and **survive reload**.
8. `npm run verify` is **green**, including the kernel, process, and shell regression suite and a new Binder `kernel-check` for the extended `wasmos:kernel` world.

## Out of scope for desktop compositor (deferred)

- **Tier B** (cooperative/Asyncify/JSPI) compositor/framebuffer path — Tier A only (R-1).
- **Networking** (OQ-2): none of the desktop compositor apps need it; brokered `net_request` is deferred. *Flagged: OQ-2 is nominally "before desktop compositor" but no desktop compositor deliverable depends on it — not a blocker.*
- **`ps`/`top` live view (FR-33)**, **IPC channels/shm at scale (FR-3 ≥32)**, **signals (FR-7)**, **session snapshot (FR-35)** — these are **process control and IPC**.
- WebGL acceleration of the framebuffer present — desktop compositor uses 2D canvas `putImageData`; WebGL is a later optimization (the surface kind is named `canvas/WebGL` to keep the door open).
- The emulator (L4 / Linux guest integration).

## Phase A — Compositor + surface + input spine (prove the riskiest paths first)

> Spine-first, exactly like shell and userland: the genuinely new and risky mechanisms are the **process→canvas framebuffer** and **input→process** paths. Build a vertical slice of each before any real app.

### Task 1 — Compositor core + window chrome + taskbar; terminal becomes a window

**Files:** `packages/host/src/compositor/{compositor.ts,window.ts,taskbar.ts,types.ts}`; `packages/host/src/compositor/compositor.css`; `packages/host/index.html` (desktop root: `#desktop`, `#taskbar`); `packages/host/src/index.ts` (boot → compositor; mount the shell and userland terminal as the first window instead of full-screen).

**Steps:**
1. `Window` model + `Compositor`: create/close/focus/move/resize/minimize/maximize, z-order stack, focus ring. DOM-surface windows host an arbitrary DOM node as content.
2. Window chrome: titlebar (pointer-drag to move), 8-direction resize handles, min/max/close buttons; double-click titlebar = maximize toggle.
3. Taskbar: launcher button (opens an app menu — wired to spawns in Task 9), a button per open window (click = focus/restore), and a live clock (updates each second).
4. Re-mount the existing xterm terminal (`term/terminal.ts`) as the content of the first window (a DOM surface), bound to the shell exactly as today.

**Tests:** `e2e/desktop.spec.ts` (real browser): boot → `#desktop` present, taskbar clock text changes within 2 s, a terminal window exists; drag the titlebar → window `transform`/geometry changes; click maximize → fills the workspace; minimize → hidden + taskbar button remains; close → window gone. (FR-21, FR-22, FR-23 DOM half.)

### Task 2 — `win_surface` + SAB framebuffer present (the spike — highest risk)

**Files:** `wit/` (`wasmos:kernel` world: add `win-surface`, `win-present` + a `surface-request` to the syscall outcome) + Binder regen; `crates/kernel/src/syscall.rs` (`0x23` WinSurface, `0x24` WinPresent; `Gpu` cap check; `SurfaceRequest` in `SyscallOutcome`), `types.rs` (`DescKind::Surface{id}`, per-process surface table), `kcore.rs`, `lib.rs` (component mapping); `packages/host/src/worker/kernel-worker.ts` (handle surface-request: ask main to make a window + framebuffer SAB; route the SAB to the process-worker; relay present signals); `packages/host/src/worker/process-worker.ts` + `wasi-shim.ts` (hold the framebuffer SAB; `win_present` copies guest mem → framebuffer SAB + signals); `packages/host/src/compositor/surface.ts` (canvas window; `requestAnimationFrame` blit from the framebuffer SAB); `packages/host/src/boot.ts` (control plumbing).

**Steps:**
1. WIT: extend the world; regenerate bindings (`npm run build`); keep p1 import shims for the new calls (FR-36, §3.4.1).
2. Kernel: `win_surface(kind,w,h)` → require `Gpu`; allocate a `surface_id`; return a `SurfaceRequest{pid, surface_id, w, h, kind}` in the outcome (mirrors shell and userland `SpawnRequest`). `win_present(surface_id, ptr, len)` → validate the surface belongs to the caller; emit a present signal in the outcome.
3. kworker: on `SurfaceRequest`, postMessage main → compositor creates a canvas window + a `w*h*4` framebuffer `SharedArrayBuffer`; the kworker hands that SAB to the owning process-worker (so the shim can write it) and the compositor keeps it (to blit).
4. process-worker/shim: `win_present` reads guest `[ptr..ptr+len]` → `framebufferSAB.set(...)` → posts a present signal through the ring outcome → compositor blits on the next rAF.
5. Spike guest: a minimal Rust `wasm32-wasip1` process that `win_surface(canvas,256,256)`, fills the framebuffer with a recognizable pattern, `win_present`s, loops a slow color cycle.

**Tests:** kernel unit tests (`win_surface` requires `Gpu` → `NOTCAPABLE` without it; returns a surface request with it; `win_present` validates ownership → `BADF`/`NOTCAPABLE` on a foreign id). `e2e/surface.spec.ts`: spawn the spike with `Gpu`; assert a canvas window appears and its pixels are non-blank (sample `getImageData` via a host hook) and change over time. **This is the desktop compositor go/no-go gate.** (FR-23 canvas half.)

### Task 3 — Input brokering (FR-25): focused canvas window → owning process

**Files:** `wit/` (`win-read-input` `0x25` + `deliver-input` host→kernel) + regen; `crates/kernel/src/{syscall.rs,types.rs,kcore.rs,lib.rs}` (`WaitReason::Input`, per-process input queue, `win_read_input` park/resume, `deliver_input` returns wakeups — siblings of shell and userland `deliver_stdin`/stdin-read; `Input` cap check); `packages/host/src/compositor/input.ts` (capture focused canvas window's pointer/key events, normalize to a compact event encoding); `kernel-worker.ts` (`deliverInput` command + wakeups); `boot.ts`/control.

**Steps:**
1. Define a compact input event encoding (type: pointer-move/down/up, key-down/up; x,y; button/keycode; modifiers).
2. Kernel: enqueue per process; `win_read_input` returns queued events or **parks** on `WaitReason::Input`; `deliver_input` enqueues + returns the woken pid (reuse the exact shell and userland wakeup plumbing).
3. Compositor: on a focused canvas window, capture pointer/keyboard, translate to surface-local coords, call `control.deliverInput(pid, bytes)` (capability-checked: owner holds `Input`).

**Tests:** kernel unit tests (read-empty parks on `Input`; `deliver_input` wakes it; re-driven read returns the event bytes; no `Input` cap → events dropped). Extend the Task-2 spike to **change color on click / on keypress**; `e2e/input.spec.ts`: focus the canvas window, dispatch real mouse+key events, assert the framebuffer reacts. (FR-25.)

## Risks specific to desktop compositor

- **Framebuffer throughput** (guest→SAB→canvas per frame). *Mitigation:* dedicated per-surface SAB (pixels never cross the ring); blit on rAF; present is a tiny signal; cap default surface size (e.g. ≤ 800×600) and document it. *Contingency:* dirty-rect present.
- **Process can't touch the DOM.** *Resolved by design:* process windows are **canvas** surfaces (FM + apps render their own UI via `wasmgfx`); only the terminal is a DOM surface — together they satisfy FR-23's "DOM **or** canvas."
- **Input focus/coordinate correctness** across overlapping windows. *Mitigation:* single-focus invariant; translate to surface-local coords in the compositor; only the focused canvas window's events are delivered.
- **Crash containment under the compositor (FR-34).** A trapping graphical process must close its window + free its surface without wedging the desktop. *Mitigation:* extend the shell and userland `proc_exit` cleanup to also release surfaces/framebuffer SABs (sibling of the shell and userland pipe-end release); covered by a Task-9 E2E case.
- **Scope.** Three sophisticated apps + compositor + two new kernel subsystems is large. *Mitigation:* spine-first (Tasks 1–3 gate everything); each app is independently demoable; the milestone is shippable after any app lands.
