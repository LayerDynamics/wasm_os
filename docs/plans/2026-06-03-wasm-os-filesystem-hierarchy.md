# WASM_OS — Unix filesystem hierarchy (implementation record)

Date: 2026-08-22
Status: implemented

## Goal

WASM_OS now has a proper, **real** (not simulated) Unix filesystem hierarchy:
`/bin /sbin /lib /usr /etc /var /tmp /opt /srv /mnt /media /proc /dev /root /run`
`/boot /home /Volumes`. Every directory is a real VFS directory on a real backend;
`/proc` and `/dev` are **real kernel-generated virtual filesystems** that reflect live
state (the actual process table, real entropy) exactly as Linux's procfs/devfs do —
never hardcoded contents. Config under `/etc` is **actually consumed** (PATH, hostname,
login banner), not decorative.

## As-built decisions

- **Depth:** real structure end-to-end, including live `/proc` + `/dev` backed by
  live kernel state. Nothing faked.
- **Dir set:** Linux FHS **+ `/Volumes`** (macOS-style mount-point dir).
- **Persistence:** persist almost everything. Ephemeral only where correctness demands
  it: `/tmp`, `/run` (scratch), `/proc`, `/dev` (synthetic), and `/bin`+`/usr/bin`+`/lib`
  (code that must match the *deployed* build — re-materialized each boot from the served
  wasm, never stale-persisted).

## Current architecture (verified in source)

- `crates/kernel/src/vfs.rs` — hierarchical tree over flat `key→bytes` backends, routed
  by **longest-prefix mount**. Backends are `Tmpfs` (in-memory), `Opfs` (`/home`),
  `Idb` (`/mnt`), and `Sys` (`/etc`, `/var`, and the other system mounts). Directories
  are implicit or explicit (`\x01d:` markers). `mkdir`/`mkdir_p`/`rmdir`/`readdir`/
  `rename` are part of the live VFS and WASI paths.
- Root `/` is `Tmpfs`. `kcore.rs:boot()` mounts `/home`→Opfs, `/mnt`→Idb, and the
  system subtrees→Sys. The host creates the separate `sys` persistent store before
  the kernel is booted.
- `/usr/bin` and `/bin` are tmpfs code paths, re-populated every boot by `index.ts`
  `loadBin`; `/sbin` receives the admin/process-control tools as well.
- `fsMkdirp` is exposed through the host control API and the guest path is backed by
  WASI `path_create_directory`.
- The shell reads `/etc/profile`, so bare-command lookup uses `/usr/bin:/bin:/sbin`.
  `/etc/motd` is written before the shell starts and is shown as the login banner.
- `/proc` is generated by `crates/kernel/src/procfs.rs`; `/dev` is handled by
  `crates/kernel/src/devfs.rs` and the VFS device read/write path. Both use live
  kernel state rather than stored fixture files.
- Entropy (`random_get`) is a host fact at the WASI-shim layer (`syscall.rs:197`), not
  the deterministic kernel — `/dev/random` routes there.

## Design

### Storage tiers (which backend each subtree mounts on)

| Tier | Dirs | Backend |
|------|------|---------|
| Persistent system | `/etc /var /opt /srv /root /usr/local /Volumes` | `Sys` store (OPFS, IndexedDB fallback) |
| Persistent user | `/home` | Opfs (existing) |
| Persistent mounts | `/mnt` | Idb (existing) |
| Ephemeral scratch | `/tmp /run` | Tmpfs |
| Ephemeral code | `/bin /sbin /usr/bin /usr/sbin /lib /usr/lib` | Tmpfs (re-materialized each boot) |
| Synthetic (live) | `/proc /dev` | kernel `procfs` / `devfs` paths |
| Structural only | `/boot /media /usr` (parents) | Tmpfs markers |

A dedicated **`Sys` store** (separate from the user `home` store) keeps system state
cleanly separated and lets `/home` stay independently wipeable. OPFS is used when
available; IndexedDB is the fallback.

### Synthetic backends (the real engineering)

The kernel has two **read-mostly** paths whose contents are generated on read from live
kernel state rather than stored:

- **`/proc`** — `readdir` lists every live PID (from `kcore` process table) + the global
  files; `read("/proc/<pid>/status")`, `.../stat`, `.../cmdline`, `.../cwd`; globals
  `/proc/meminfo`, `/proc/uptime`, `/proc/mounts`, `/proc/self`, `/proc/version`,
  `/proc/cpuinfo`. Backed by the **actual** `procs`/`sched` state — same source as
  `listProcs`. Writes rejected (EROFS) except where Linux allows.
- **`/dev`** — device nodes with **real** semantics handled at the fs-op layer:
  `/dev/null` (writes discarded, reads EOF), `/dev/zero` (reads zero bytes), `/dev/full`
  (writes ENOSPC), `/dev/random`+`/dev/urandom` (reads → real host CSPRNG via the
  existing entropy path), `/dev/tty` (the terminal). `readdir(/dev)` lists the nodes.

The process table remains owned by the kernel. `procfs` receives that table for reads,
while `devfs` classifies device operations and the VFS/syscall layer applies their
semantics. This keeps `/proc` and `/dev` live without putting host state in userland
files.

## Implementation record — completed tasks

### Task: add directory creation and the system store
- Added `mkdir`/`mkdir-p` to the WIT interface and kernel exports, wired the
  `fsMkdirp` host control operation, and added the third `sys-store` binding.
- Verified that `/etc` writes route to the system store independently of `/home`.

### Task: mount and materialize the FHS
- `kcore.rs:boot()` mounts each subtree and creates the standard directories so `ls /`
  exposes the hierarchy immediately.
- Persistent files in `/home`, `/mnt`, and system mounts survive reload; tmpfs code and
  scratch paths are recreated at boot.

### Task: consume `/etc` configuration
- The host seeds `/etc/os-release`, `/etc/hostname`, `/etc/motd`, `/etc/profile`, and
  `/etc/passwd` without overwriting user edits.
- The shell uses the profile path, and the login banner reads the real motd file.

### Task: install executable guests in the FHS paths
- `loadBin` installs guests into `/usr/bin` and `/bin`; admin/process-control tools also
  go into `/sbin`.
- The shell resolves commands across the configured path, and the file manager launches
  executables from the VFS.

### Task: expose live `/proc`
- `procfs` lists the live process table and exposes status, stat, cmdline, uptime, mounts,
  version, and related kernel views.
- Reads through the shell and host control path see current process state.

### Task: expose live `/dev`
- `devfs` exposes null, zero, full, random, urandom, and tty with their device semantics.
- Random data is seeded from host entropy; writes to read-only or synthetic paths are
  rejected where appropriate.

### Task: make the hierarchy visible
- `mount` reads the live mount view, `/var/log/boot.log` records the current boot facts,
  and the Welcome app describes the filesystem.

### Task: preserve data and verify the live paths
- Capability checks apply to the mounted tree, and `/proc`/`/dev` keep their default
  read/write restrictions.
- Existing `/home` data remains intact while the system store is introduced.

## Risks / notes
- **`/bin` must stay ephemeral** even under "persist everything": persisting code risks
  serving stale guests after a deploy. Re-materialize from the served wasm each boot.
- The `/proc` and `/dev` generators stay in the kernel, not the host, so their contents
  remain tied to live kernel state.
- Cross-backend `rename`/`cp` already returns a clear error; document that moving across
  tiers is copy+unlink at the shell layer.
